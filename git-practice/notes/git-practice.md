# Git 学习笔记

## 一、Git 的作用

Git 是分布式版本控制工具，用于记录文件随时间发生的变化。每次提交都保存一个可以追溯的版本，并记录提交者、时间、说明和父提交等信息。

在学习和开发中，Git 可以帮助我：

- 对比修改前后的差异，查找改动原因。
- 根据提交历史定位某个功能或问题是在什么时候引入的。
- 使用分支尝试新的修改，并在确认后合并。
- 与其他人协作开发，通过远程仓库交换提交。
- 在本地完成提交，再选择合适的时间推送到远程。

Git 是版本控制工具；GitHub 和本次使用的教学平台是托管 Git 仓库的服务。使用 Git 并不要求每次提交时都能连接网络。

## 二、工作区、暂存区和本地仓库

| 区域 | 保存什么 | 本次练习中的例子 |
| --- | --- | --- |
| 工作区 | 当前能够看到和编辑的文件 | 在编辑器中修改 `git-practice.md` |
| 暂存区 | 准备进入下一次提交的文件内容 | 执行 `git add` 后保存的修改 |
| 本地仓库 | 已经提交的版本及其历史 | 执行 `git commit` 后生成的提交记录 |

基本流程：

```text
编辑并保存文件
    ↓ git add
暂存本次准备提交的内容
    ↓ git commit
生成本地提交
    ↓ git push
把提交发送到指定远程仓库
```

这里最容易混淆的是：**保存文件、暂存、提交和推送是四个不同的动作。** 文件保存后不一定已暂存；已暂存不代表已提交；已提交也不代表已上传到 GitHub。

例如，先写入 A 内容并执行 `git add`，然后又把文件改为 B 内容，如果没有再次暂存，下一次提交仍然只包含先前暂存的 A 内容，B 中新增的修改还留在工作区。

## 三、查看状态与差异

### 1. `git status`

```bash
git status
git status --short --branch
```

用于查看当前分支、未跟踪文件、已修改但未暂存的文件，以及已经暂存的修改。

短格式常见状态：

| 标记 | 含义 |
| --- | --- |
| `??` | 文件尚未被 Git 跟踪 |
| ` M` | 已跟踪文件在工作区中被修改，但尚未暂存 |
| `M ` | 修改已经暂存 |
| `A ` | 新文件已经暂存 |
| `MM` | 既有已暂存修改，也有之后尚未暂存的修改 |

短格式的第一列主要表示暂存区状态，第二列表示工作区状态。查看状态应成为提交前后的固定习惯。

### 2. `git diff`

```bash
git diff
git diff --cached
git diff --stat
```

- `git diff`：查看已跟踪文件在工作区中相对暂存区的差异。
- `git diff --cached`：查看暂存区相对当前提交的差异，即下一次提交准备包含的内容。
- `git diff --stat`：按文件概览尚未暂存的修改量。

尚未跟踪的新文件通常不会直接出现在普通 `git diff` 中，因此要结合 `git status` 检查。

## 四、暂存与提交

### 1. `git add`

```bash
git add git-practice/notes/git-practice.md
git add .gitignore
```

`git add` 将指定路径当时的内容加入暂存区。它既可用于开始跟踪新文件，也可用于暂存已跟踪文件的修改。

本次练习优先指定具体文件路径，方便把一次提交控制在一个明确主题内，减少误加入其他文件的机会。

### 2. `git commit`

```bash
git commit -m "docs: 添加 Git 练习笔记"
```

`git commit` 根据暂存区生成本地提交。它不会自动上传代码，也不会把未暂存的修改一并提交。

本次采用的提交说明形式为：

```text
类型: 本次完成的具体事项
```

- `docs:`：用于笔记、报告和操作记录等文档修改。
- `chore:`：本次用于 `.gitignore` 等仓库配置维护。

这种格式是本次练习采用的约定，并不是 Git 强制要求。相比 `test`、`111`、`update`，具体的说明更容易让人理解每次提交的目的。

### 3. 一次提交的检查顺序

```bash
git status
git diff
git add git-practice/notes/git-practice.md
git diff --cached
git commit -m "docs: 完善 Git 学习笔记"
git status
```

先明确改动，再确认准备提交什么，最后检查提交后是否仍有遗留修改。

## 五、`.gitignore` 的用途与边界

`.gitignore` 用于声明通常不需要跟踪的文件或目录。本次放在仓库根目录，内容如下：

```gitignore
node_modules/
dist/
.env
*.log
```

- 末尾的 `/` 表示匹配目录，例如 `dist/`。
- `*` 是通配符，`*.log` 可以匹配不同名称的日志文件。
- 这些规则没有以 `/` 开头，因此在其适用范围内也可匹配子目录中的对应名称。
- `.gitignore` 本身需要提交，让使用仓库的人共享这些规则。

特别注意：忽略规则主要作用于尚未跟踪的文件。如果文件已经被 Git 跟踪，后来添加忽略规则不会让它自动停止跟踪，更不会清除历史中的内容。

可以用下面的命令检查某个路径匹配了哪一条规则：

```bash
git check-ignore -v example.log
```

这只是检查路径是否匹配，不要求我真的创建这个日志文件。

## 六、Git 分支

### 1. 什么是分支

分支可以理解为指向某个提交、并随着新提交向前移动的名字。它为不同的修改提供相对独立的开发路线，并不会在磁盘上自动复制出另一份项目文件夹。

本次同时存在名为 `git-practice` 的目录和分支，两者含义不同：目录组织文件，分支组织提交历史。

### 2. 为什么使用分支

开发新功能、修复问题或尝试方案时，可以先在独立分支修改和提交。完成检查后，再将结果合并到主分支，使每项工作更容易管理和追踪。

### 3. 创建和切换分支

```bash
git switch -c git-practice
git branch
```

`git switch -c` 创建分支并切换过去；`git branch` 列出本地分支，`*` 标记当前分支。

旧命令也可以完成相同操作：

```bash
git checkout -b git-practice
```

如果分支已经存在，直接切换即可，不再使用创建参数：

```bash
git switch git-practice
```

切换前先检查并妥善处理未提交的修改。切换分支不一定会清空工作区修改；某些修改可能随切换保留，而与目标分支冲突的修改可能使切换被阻止。

### 4. 合并分支

```bash
git switch master
git merge git-practice
```

先切换到接收修改的分支，再执行合并。在本例中，是把练习分支纳入 `master`。

快进合并发生在当前分支的提交是目标提交的祖先时，可以直接把当前分支指针向前移动，因此不一定生成新的合并提交。

如果两边各自增加了提交，Git 可能创建合并提交；如果修改存在无法自动协调的冲突，就需要人工处理后再完成合并。本次练习已有历史呈线性结构，没有记录人工解决合并冲突的过程，因此不把冲突处理写作已完成操作。

查看哪些分支已经合入 `master`：

```bash
git branch --merged master
```

输出中包含 `git-practice`，说明这个分支当前指向的提交已经被 `master` 包含。合并并不意味着删除练习分支。

## 七、查看提交记录

```bash
git log --oneline
git log --oneline --graph --decorate --all
```

- `--oneline`：用简短提交编号和说明展示记录。
- `--graph`：用文本线条展示提交之间的关系。
- `--decorate`：显示分支等引用标签。
- `--all`：查看本地已知的各引用所能到达的历史，不会主动联网刷新远程记录。

`HEAD` 通常指向当前检出的分支。`master` 和 `git-practice` 指向不同的提交，不代表其中一个分支丢失；本次主分支在纳入分支笔记后，还继续增加了总结和截图提交。

远程跟踪引用，例如 `github/master`，是本地记录的远程分支状态，可能因为远程之后发生了变化而过期。判断远程最新状态时，不能只依赖一份旧的本地记录。

## 八、本地仓库、远程仓库与认证

### 1. `init`、`clone`、`commit` 和 `push`

| 命令 | 用途 |
| --- | --- |
| `git init` | 在普通目录中初始化一个 Git 仓库 |
| `git clone 地址` | 将已有远程仓库克隆到本地 |
| `git commit` | 把暂存内容保存为本地提交 |
| `git push 远程名 分支名` | 把本地提交和分支更新发送给远程 |

本次从已有仓库开始练习，不需要再次执行 `git init`。之后在 GitHub 创建一个空的托管仓库，只是为已有本地历史增加新的存放位置，不需要重建本地提交历史。

### 2. 远程地址与远程连接名

```bash
git remote -v
```

`origin` 是常见的远程连接名，不是固定写死的服务器，也不是账号名称。本次有两个连接：

| 连接名 | 目标 |
| --- | --- |
| `origin` | 教学平台的作业仓库 |
| `github` | 自己的 GitHub 仓库 |

因此向 GitHub 推送时使用：

```bash
git push github master
```

首次使用 `git push -u github master`，还会为本地 `master` 设置上游关系。仓库同时连接多个远程时，明确写出远程名和分支名更容易看清目标。

### 3. HTTPS 和 SSH

HTTPS 使用账号及密码或令牌等凭据认证，具体要求由平台决定。GitHub 的 Git HTTPS 操作不能使用普通账号密码，可以使用个人访问令牌或凭据管理器完成认证。

SSH 使用本地私钥及添加到平台账号中的公钥完成认证。公钥文件通常以 `.pub` 结尾；私钥留在本地，不应放入作业或仓库。

需要区分三个问题：

1. **远程地址**：要访问哪个仓库？
2. **身份认证**：服务器把当前操作识别为哪个账号？
3. **权限检查**：这个账号能否读取或写入目标仓库？

认证成功不等于有写入权限。`git config user.name` 和 `user.email` 主要用于提交作者信息，也不能用来确认当前网络认证账号。

## 九、本次遇到的问题与处理方法

### 1. 教学平台 HTTPS 认证失败

克隆时出现双重认证提示，普通账号密码不能用于该次 HTTPS 认证。改用平台提供的 SSH 地址后成功克隆，说明后续可以继续在本地完成练习。

### 2. 可以克隆，但不能推送

SSH 推送时出现 `You do not have sufficient authorization for this action`。克隆只需要读取权限，推送还需要写入权限，因此能下载并不能证明能上传。

经过核对，仓库路径没有发现拼写错误。SSH 实际使用的账号和仓库授权仍需核实。HTTPS 还出现过 HTTP 403，可能涉及权限或平台入口配置，不能只凭这一条信息断言账号密码错误。

教学平台推送问题没有被确认解决；本次保留原有仓库及历史，并将练习成果推送到自己的 GitHub 仓库。

### 3. `remote origin already exists`

已有名为 `origin` 的连接，再次执行同名 `git remote add` 会失败。解决办法是为 GitHub 使用新的连接名 `github`，而不是反复添加 `origin`。

### 4. GitHub 添加公钥提示已存在

公钥可能已经添加到 GitHub，无须反复添加同一把公钥。可以执行：

```bash
ssh -T git@github.com
```

检查返回信息中的 GitHub 用户名是否为自己的账号。认证成功提示中出现不提供 shell 访问，是 GitHub 的正常行为。

### 5. 上传显示 100%，但仍然报错

`Writing objects: 100%` 表示客户端完成了相应数据写出，并不能单独证明远程分支更新成功。如果同时出现 HTTP 错误或连接中断，应核查远程分支，而不能只看最后一行 `Everything up-to-date`。

只读核对命令示例：

```bash
git rev-parse master
git ls-remote github refs/heads/master
```

比较本地 `master` 的提交编号和远程返回的编号；相同表示两者当前指向同一个提交。

## 十、练习后的操作习惯

- 操作前先确认终端所在目录、当前分支和远程连接。
- 编辑文件后先保存，再暂存和提交。
- 提交前检查暂存内容，让一次提交对应一个清晰目的。
- 合并前确认练习分支已经提交，并切换到接收修改的分支。
- 通过提交历史判断练习结果，不把“没有新的合并提交”当成失败。
- 将本地操作与网络认证分开排查，保留错误信息，不盲目重复推送。
- 提交作业前检查文档路径、忽略规则、截图以及最终仓库状态。

本次练习让我从只关注“文件有没有上传”，逐步转向理解“文件如何变成一次可追溯的提交，以及提交如何在分支和远程仓库之间流转”。
