### 优化一：只读参数改为 const 引用

**问题：**字段访问的 `operator[] → proxy → const_proxy` 传参链按值复制字符串。基线 MTuner 按最近 JSON 源码帧归类，两个参数复制位置各触发 104 次分配。

**原因分析：**`const std::string key` 只限制函数内不能修改参数副本，并不避免复制。字段名沿调用链传递时，就可能重复构造字符串；本机 Debug 下，即使字符能放进短字符串存储，字符串对象仍可能申请 `std::_Container_proxy` 调试代理，因此短字段名也会出现堆分配。

**修改：**在 `json.h` 中将 22 处只读参数改为 `const &`，覆盖字符串、对象和数组参数。代理成员及需要长期保存的值仍独立拥有数据，避免引用临时输入。

典型签名由 `const_proxy(const jobject &source, const std::string key)` 改为 `const_proxy(const jobject &source, const std::string &key)`。只借用调用期间的输入，代理自身保存的键仍按原方式复制。

**结果：**读取字符串由 8 次降至 6 次分配，读取整数由 4 次降至 2 次；解析和序列化数据未变化，整套峰值也未下降。

解析实验使用 `parse(input.c_str())`，没有经过本轮调整的 `std::string` 输入重载，所以不能期待所有实验同步改善。整套少了 208 次分配，与上述两处各 104 次的参数复制对应。

### 优化二：减少解析过程中的临时复制

**问题：**子 reader 读出副本后再追加，`parse_results → entry → 容器` 又连续复制同一字符串。优化一报告中，按最近 JSON 源码帧归类的 `reader::readout()` 路径有 33,819 次分配，是进一步查看源码的线索。

**原因分析：**这些临时结果很快就会销毁，却在交接时再次申请存储、复制内容。每个字段都经过相似路径，因此局部的一次复制会被放大为大量分配；如果目标和临时副本短时共存，还可能增加瞬时用量。这里应区分调用者需要保留的输入与解析器内部可以交出的临时数据。

**修改：**子 reader 直接追加内容；仅在内部临时对象不再使用时交出缓冲区、移动值或条目，并删除未使用的局部 reader。公开 `readout()`、插入操作及自定义 reader 的行为保留。

交接前先取得类型等仍要使用的信息，再转移字符串；内部插入仍执行原来的校验。公开接口继续返回独立副本或复制输入，避免为了内部省内存而改变调用者源对象的状态。

**结果：**100 字段解析由 3,185 次降至 2,484 次分配，累计申请由 108,924 B 降至 89,708 B；整套峰值仅小幅变化。

### 优化三：按实际内容规划容量

**问题：**容器与字符串反复扩容，产生重复申请、元素搬迁和新旧缓冲区短时并存。

**原因分析：**优化二之后，分配栈仍反复出现容器插入触发的 `vector` 扩容，字符串也逐字符或逐字段追加。减少复制还不够：如果最终需要的空间比较明确，可以提前预留，减少增长过程中的多次申请；但预留过大又会增加存活内存，需要结合实际内容估算。

**修改：**扫描当前层条目数，为解析容器预留容量；已知数量的键列表、编解码字符串和输出缓冲区也按实际内容估算容量。扫描只提供容量提示，不参与合法性判断，不把嵌套内容、字符串内逗号或后缀计入本层数量。

解码只估算当前字符串，格式化输出对嵌套值使用保守估算，避免为最终会去掉的空白预留大量空间。估算不确定或长度加法溢出时放弃提示，由原来的增长和解析逻辑继续处理。

**结果：**100 字段解析降至 1,904 次分配、54,526 B 累计申请；整套峰值降至 132,645 B。

### 优化四：序列化直接写入输出缓冲区

**问题：**字段拼接先生成临时字符串，再追加到结果；嵌套格式化还会生成完整子字符串，增加中间存储。

**原因分析：**优化三已为最终输出预留容量，但 `encode_string(key) + ":" + value + ","` 这样的表达式仍会先构造中间结果。最终缓冲区有足够空间，并不能阻止这些临时字符串分配。格式化嵌套对象时，先返回完整子串再复制，也存在同类开销。

**修改：**编码、键、标点和值直接追加到最终缓冲区，嵌套格式化递归写入同一缓冲区，复用优化三的容量规划。保持字段顺序、缩进以及原库的转义、空容器和错误行为。

字符串编码共用直接追加的函数，分隔符在需要的位置写入，数组赋值的序列化也避免“元素加逗号”的副本。兼容性上，保留 `pretty()` 原来的键输出规则及已有 NUL 截断行为，不顺带修复这些功能细节。

**结果：**紧凑输出由 353 次降至 3 次分配，格式化输出由 153 次降至 3 次。整套峰值仍为 132,645 B，说明本轮减少了高频申请，但没有消除决定全局峰值的存活数据。

### 优化五：消除解析返回时的整对象副本

**问题：**Debug 调用栈显示，命名局部对象 `return result` 未应用 NRVO 时，会复制整个 `jobject`，原结果和完整副本短时同时存活。

**原因分析：**前四轮分配次数已明显减少，峰值却仍为 132,645 B，因此继续只减少小临时对象未必有效。复核发现 `runOnce() → jobject::parse() → jobject 复制构造 → vector/字符串深复制` 的返回路径：解析结束后，已有完整结果又被复制一份，这比单个字段的临时申请更可能推高峰值。

**修改：**增加私有构造函数接收即将销毁的内部容器，以 `return jobject(std::move(result.data), result.array_flag)` 直接构造返回对象，利用 C++17 返回值消除规则。没有增加公开移动构造或移动赋值，调用者的复制及显式 `std::move` 行为保持原样。

仅将返回语句改成 `std::move(result)` 并不能解决：原类没有可用的公开移动构造，仍会调用复制构造。本轮在内部转移容器，再直接构造返回值，避开这条深复制路径，也不依赖可选的命名返回值优化。

**结果：**整套峰值由 132,645 B 降至 94,282 B。这一轮直接减少了峰值时的重复存储。

### 优化六：内部键使用紧凑的独立存储

**定位依据：**优化五的峰值发生在 100 字段对象解析阶段。峰值存活堆中，字符缓冲约占 51.0%，Debug 容器代理约占 31.2%，五个 vector 的元素存储区约占 17.8%。因此，`reserve()` 是申请入口，不能据此认定它贡献了大部分峰值；删除预留反而可能重新引入扩容开销。

**原因分析：**检查当前样本时，预扫描条目数与实际数量一致，没有发现预留数量膨胀。峰值同时包含正在解析的对象和提前创建的常驻对象；若常见键各自持有字符缓冲和调试代理，缩小键的长期存储就能同时减少这两部分，而不只是少一个临时变量。触发峰值的最后一次小申请，也不能独自解释此前已存活的大量内存。

**修改：**私有键类型 `StoredKey` 将 22 字节以内的键存于自身数组，长键通过 `unique_ptr<std::string>` 独立拥有。内部元素改为 `pair<StoredKey, std::string>`，减少常见键的字符缓冲与调试代理开销。公开 `json::kvp`、值的 `std::string` 类型及 `entry::ref()` 保持不变。

只调整私有键表示，是因为值的 `entry::ref()` 返回 `const std::string&`，替换值类型可能破坏引用有效性。键的比较和格式化输出仍按完整长度处理；输入销毁后结果仍有效，复制长键时也创建独立存储。

**兼容要求：**键不能直接改成借用输入的裸 `char*`，否则可能破坏生命周期、复制和带长度的字符串语义。长键仍走独立分配路径，本方案的收益需结合实际键长分布判断。

长键是实际代价：此前独立 Debug 样例中，复制 23 字节键由 2 次分配变为 3 次。因此不能宣称任意 JSON 都更省内存。本轮峰值降幅较大，主要是短键保存到最终结果和常驻对象后，不再长期持有原来的独立堆块。

**结果：**整套峰值由 94,282 B 降至 61,978 B；100 字段解析累计申请由 36,879 B 降至 34,479 B。

| --------------------- | -------: | ---------------: | -------: |

### 优化七：内部解析结果交接与保守的缓冲复用

**问题：**每个键、值分别构造临时解析结果；键解码后丢弃编码缓冲，随后读取值时再次申请。

**原因分析：**优化六改变了最终存储，读取过程中的 reader、`parse_results` 和编码字符串仍会反复创建。说明“结果保存得更紧凑”和“生成结果时少申请”是两个问题。本轮继续检查临时数据的使用顺序，尝试复用已完成用途的对象和缓冲。

**修改：**循环外持有独立拥有数据的 token，内部解析直接写入并交接结果；共享原有读取和校验过程。仅在下一字符串大小合适时复用编码键缓冲，避免长键后的短值长期保留过大容量。

私有 `ReadTokenInto()` 直接写入已有结果，`ReadTokenContents()` 共用原来的读取、校验和剩余输入更新过程。探索中发现，4096 字节键后接 `"x"`，盲目交换缓冲会让短值保留很大容量，因此非字符串、小值及容量不合适的情况不复用，并加入反例回归。

**结果：**整套分配次数由 122,189 降至 82,662，峰值仍为 61,978 B。包含“长键后接短值”的容量反例回归，保留公开 reader 和解析接口。

峰值存活块的字符缓冲、代理和容器存储与优化六相同，说明本轮主要减少反复创建和释放，尚未缩小决定最高点的长期存储。

### 优化八：独占 token 内解码键，直接构造最终条目

**问题：**键进入最终容器前，仍经过编码 token、解码字符串和临时 `kvp`，中间字符串带来额外分配。

**原因分析：**优化七复用了部分读取缓冲，但键解码仍另建字符串，进入最终条目时又经过临时键值对。已校验的编码 token 由当前调用独占，解码后的内容不会比编码内容更长，因此可以研究在同一缓冲区中完成解码，再直接构造最终存储，进一步减少过渡对象。

**修改：**已校验的键在内部独占 token 中原地解码，公共解码接口与内部路径共用解码逻辑；短键进入 `StoredKey`，长键按解码后长度独立存储，键和值直接构造最终条目。仅修改 `json.cpp`，调用者输入不变，也不长期保留过大的转义缓冲。

原地解码时，写入位置不越过未读取的位置，读取结束后才缩短字符串。共享 `DecodeBytes()` 保留原来的转义、Unicode 处理和错误规则；长键重新按解码后长度存储，避免直接接收编码缓冲而留下过多容量。

**结果：**整套分配次数由 82,662 降至 42,980，峰值由 61,978 B 降至 61,758 B；100 字段解析由最初 3,185 次、108,924 B 降至 404 次、15,295 B。值仍为 `std::string`，未采用短值缓存等探索方案。

本轮分配次数下降约 48.01%，峰值仅下降约 0.35%：常驻对象和固定输入没有缩小，主要变化仍是临时分配。RelWithDebInfo 补充测量中，100 字段解析也由 201 次降至 101 次，说明收益不全来自 Debug 调试代理。
